# A 股盘后市场概览（验证版）设计

日期：2026-07-07
最后修订：2026-07-14
状态：已批准，待分阶段实现

## 1. 产品定义

第一版产品名称为 **A 股盘后市场概览（验证版）**。

它面向普通市场观察者，帮助用户在 5 至 10 分钟内理解：

- 当天核心指数和市场温度如何变化；
- 哪些板块相对强弱；
- 官方或交易所是否出现经确认的新事项；
- 哪些信息已经验证，哪些覆盖存在缺口；
- 每条结论可以追溯到什么来源和原始快照。

“Loop Engineering”是开发与质量改进方法，不是面向用户的价值承诺。产品不得提供买卖、目标价、个股推荐或仓位建议。

## 2. 第一版边界

真实数据模式第一版只支持 `after_close`。fixture 教学模式继续支持 `after_close` 和 `pre_open_update`。

真实数据模式包含：

- 上证指数、深证成指、创业板指；
- 至少一组市场温度指标；
- 板块强弱；
- 官方或交易所来源检查；
- 官方事项候选项的人工确认；
- 来源、快照、事实、报告与反馈的审计链。

真实数据模式暂不包含：

- 重大媒体新闻和机构观点自动采集；
- 自动生成市场涨跌原因；
- 完整风险解释；
- 真实盘前更新；
- 多用户身份、权限和个性化；
- 自动定时、推送或公网生产部署；
- LLM 对官方文件的总结。

页面必须明确显示未覆盖模块，不用空洞模板制造完整简报的错觉。项目仓库名称可以保持 `market-daily-briefing`，因为它代表长期方向。

## 3. 运行环境与许可边界

真实数据 MVP 限定为本地、非商业、单维护者验证环境。

每个真实来源接入前必须登记：

- 实际数据提供方，而非仅登记调用工具或 SDK；
- 访问方式和原始 URL/API；
- 许可或服务条款链接；
- 是否允许抓取、保存、展示和再分发；
- 频率限制和署名要求；
- 审查日期与结论。

许可未确认的数据只能用于本地评测，不得进入公开部署。公开部署和多人开放必须经过单独设计与许可审查。

## 4. 运行模式

系统保留三个来源模式：

1. `fixture`
   - 使用确定性样例；
   - 用于教程、回归测试和可复现排错；
   - 可以覆盖盘后和盘前报告。

2. `mock_real`
   - 运行真实管线逻辑，但注入假客户端和固定响应；
   - 默认测试套件使用该模式，不访问网络；
   - 用于验证双源核对、人工审核、警告和失败门禁。

3. `real`
   - 使用已登记且许可允许的真实来源；
   - 第一版只允许 `after_close`；
   - 不得静默回退到 fixture。

CLI 与 Web 必须调用同一管线服务，入口层不得复制发布规则。

## 5. 审计不变量

### 5.1 运行记录

- 新运行开始前检查 `run_id`；已存在时立即拒绝。
- run 在终态之前只能按允许的状态机迁移。
- `COMPLETED`、`COMPLETED_WITH_WARNINGS`、`FAILED` 等终态不可修改。
- 修订必须创建新 run，并记录 `supersedes_run_id` 或等价关系。
- 已发布事实和报告只允许插入，不允许 `upsert` 覆盖。

建议状态机：

```text
CREATED -> RUNNING -> AWAITING_REVIEW -> COMPLETED
                   -> COMPLETED_WITH_WARNINGS
                   -> FAILED
```

没有官方候选项时可以从 `RUNNING` 直接进入完成状态。有候选项时，必须全部被批准或拒绝后才能发布。

### 5.2 原始快照

每份快照必须保存：

- `snapshot_id`、`run_id`、模块和来源；
- 实际数据提供方与原始 URL/API；
- 抓取时间、内容类型和交易日或发布时间；
- 不可变文件路径；
- `sha256` 内容哈希；
- 许可登记引用和来源口径元数据。

采集先写入 run 专属暂存区。发布门禁通过后，快照进入正常审阅账本；失败运行的材料移动到明确标记的诊断区，不出现在正常报告或来源索引中。

### 5.3 原子可见与恢复协议

SQLite 与文件系统不能组成真正的跨资源原子事务。本项目以数据库为“正常审阅账本是否可见”的唯一判据，并使用以下发布协议：

1. 在暂存区完成采集、审核、报告生成、哈希和全部门禁；
2. 将通过门禁的 run 目录原子重命名到最终不可变路径；
3. 在单个 SQLite 事务中插入快照、事实、报告、警告引用，并迁移到最终 run 状态；
4. 只有数据库事务成功后，run 才对正常审阅界面可见；
5. 启动或发布前执行恢复扫描：最终路径中没有已发布 run 引用的目录属于孤立目录，校验后移入诊断区；
6. 数据库已引用但最终文件缺失或哈希不符属于审计损坏，必须阻断展示并报警，不能自动重建或覆盖。

任何门禁或校验失败，都不得留下“报告未发布但正常账本已有部分事实”的状态。

## 6. 候选项与已发布事实

内容性质和验证状态必须分离。

### 6.1 采集候选项

官方与交易所采集结果先形成 `EvidenceCandidate`，建议包含：

- `candidate_id`、`run_id`、`snapshot_id`；
- 标题、详情 URL、发布时间、直接摘录；
- 模块和建议内容类型；
- 审核状态 `pending / approved / rejected`；
- 审核时间、审核备注和本地维护者标识；
- 批准后生成的 `fact_id`，如有。

候选项状态变化必须保留审核事件，不得通过覆盖原记录抹去历史。

### 6.2 已发布事实

已发布 `AtomicFact` 的内容类型为：

- `FACT`：直接观测或经确认的事实；
- `OPINION`：明确归属于某主体的观点；
- `INFERENCE`：由一个或多个已发布事实推导的归纳或推测。

`UNVERIFIED` 不再作为已发布内容类型。为兼容旧 fixture，可以暂时读取该值，但不得让它进入真实模式的正式报告。`confidence` 只描述证据强弱，不表示审核状态。

官方候选项批准后新建不可变事实，并指回候选项和原始快照。被拒绝候选项保留审计记录，但不进入报告。

## 7. 市场数据策略

### 7.1 核心指数硬门槛

以下三个指数必须完整：

- 上证指数 `000001.SH`；
- 深证成指 `399001.SZ`；
- 创业板指 `399006.SZ`。

每个指数必须包含交易日、收盘点位和涨跌幅。交易日必须与报告日期匹配；非交易日运行需要明确拒绝或选择最近交易日，不能把旧数据标成当天数据。

核心指数必须来自两个相互独立、已登记的实际数据提供方。两个来源在按报告展示精度四舍五入后，收盘点位和涨跌幅必须一致。若冲突，运行进入 `FAILED` 或人工诊断，系统不得自行挑选一个值。

AkShare 可以作为调用工具，但 `AkShare adapter` 不能代替实际数据提供方出现在审计记录中。

### 7.2 可降级覆盖项

市场温度至少设计两类采集能力：

- 两市成交额及较前一交易日变化；
- 上涨家数与下跌家数。

第一版至少成功一类即可正常完成；全部缺失时允许 `COMPLETED_WITH_WARNINGS`，并在对应章节显示缺口。

板块强弱应包含涨幅与跌幅靠前板块。板块允许单一来源，但必须显示供应商、板块分类体系、统计时间和口径。板块数据缺失时允许带警告完成。

## 8. 官方与监管来源策略

官方来源采用“列表页 + 详情页”采集：

1. 检查公告或信息列表页；
2. 提取时间窗口内项目的标题、链接和发布时间；
3. 抓取详情页并保存第二份快照；
4. 提取可直接核对的短摘录；
5. 形成候选项，等待人工确认。

官方检查必须产生三种可区分结果：

- `checked_no_updates`：检查成功，时间窗口内没有新增事项；
- `candidates_found`：发现候选项，等待审核；
- `check_failed`：来源不可达或解析失败。

政策或监管事实不是每日发布硬门槛：

- 无新增时显示“已检查，未发现新增事项”；
- 部分或全部检查失败时允许市场报告带警告发布，并明确覆盖不完整；
- 未经人工确认的候选项不得成为高置信度事实。

发布时间窗口以中国市场时区定义，并在实现计划中用测试固定边界。首页标题、导航文字或首个段落不能仅因解析成功就成为事实。

## 9. 发布门禁

真实盘后报告只有满足以下条件才允许发布：

- run ID 唯一且状态迁移合法；
- 三个核心指数完整、交易日正确且双源一致；
- 所有待审核官方候选项已处理；
- 所有已发布事实都指向存在且哈希可验证的快照；
- 推测具有完整、存在于当前发布账本中的派生链；
- 报告章节分类规则和投资建议禁令通过；
- 警告和缺失覆盖项被明确写入运行元数据与界面。

失败时不得发布正常报告。市场温度、板块或官方检查失败属于可降级项，进入 `COMPLETED_WITH_WARNINGS`。

## 10. 警告与覆盖状态

警告必须结构化持久化，不能只塞入 `error_message`。建议 `run_warnings` 包含：

- `warning_id`、`run_id`；
- `source_name`、`module`；
- 面向用户的 `message`；
- 可选诊断 `detail`；
- `created_at`。

用户界面使用格式：

```text
<来源名称> / <模块> / <错误摘要>
```

运行还应保存模块覆盖状态，使界面能区分：已覆盖、无新增、待审核、检查失败、暂未支持。面向用户的页面不得显示 Python 堆栈。

## 11. 报告结构与界面

真实盘后概览至少包含：

1. 今日核心事实；
2. 核心指数；
3. 市场温度；
4. 板块强弱；
5. 官方与监管检查结果；
6. 覆盖缺口与运行警告；
7. 来源与审计链；
8. 上一轮反馈执行回执。

Web 工作台增加：

- 独立的真实盘后运行入口；
- 官方候选项审核队列；
- 双源核对结果；
- 快照哈希与来源登记信息；
- 覆盖状态与警告；
- fixture/真实数据的醒目标识。

fixture 的教学界面可继续展示事实、观点、推测和盘前示例，但不得与真实数据报告混淆。

## 12. 反馈闭环

第一版反馈属于单维护者质量闭环，不声称支持多用户自适应。

反馈只能改变：

- 章节长度和表达密度；
- 章节展示优先级；
- 在既有安全边界内的覆盖检查优先级；
- 引用与派生链的可见程度。

反馈不得改变：

- 原始数据、事实分类或审核结果；
- 来源可信度和双源核对结果；
- 发布门禁或投资建议禁令。

反馈标签应编译为结构化 `FeedbackDirective`，而不是把用户原文直接拼入 LLM 提示。下一轮报告必须记录每条指令的 `applied / not_applied` 状态和原因。

未来多用户版本需要把个人偏好与全局质量改进分层，并对反馈输入实施身份、隐私、聚合阈值和提示注入防护。

## 13. 质量评测

真实数据 MVP 发布前必须建立 10 个代表性交易日的黄金评测集，覆盖至少：

- 普涨、普跌；
- 放量、缩量；
- 板块分化；
- 有重要官方事项；
- 无官方新增；
- 来源失败或双源冲突等降级场景。

黄金集由人工核验并保存来源证据。自动评测硬指标：

- 核心数值准确率 100%；
- 来源与交易日匹配率 100%；
- 事实、观点、推测误分类为 0；
- 硬门禁漏拦截为 0；
- 缺失覆盖项全部显式显示；
- 快照哈希校验通过率 100%。

人工评分只用于清晰度、简洁度和重点覆盖，不替代事实正确性。反馈闭环评测必须证明表达确实变化，同时事实覆盖和正确性不下降。

## 14. 实施顺序

依赖顺序固定为：

1. 审计底座与候选事实模型；
2. 黄金评测骨架与发布门禁；
3. 真实市场数据、官方采集和人工审核；
4. 可执行反馈闭环。

生产网络接入位于第三阶段。不得为了尽快显示真实数据而绕过前两阶段。

## 15. 验收标准

- fixture 原有教学路径继续可用。
- real 模式只允许盘后概览，不支持真实盘前更新。
- 重复 run ID 被拒绝，终态记录不可覆盖。
- 每份快照具有可复算的 SHA-256 哈希。
- 失败运行材料不进入正常审阅账本。
- 三个核心指数经过双来源、交易日和完整性校验。
- 市场温度、板块和官方检查缺失时正确降级并显示警告。
- 官方事项经人工批准后才成为已发布事实。
- 无官方新增与官方检查失败在数据模型和界面上清晰区分。
- 正式报告不包含 `UNVERIFIED` 类型的已发布事实。
- 10 日黄金评测集全部通过硬指标。
- 反馈产生可观察的表达变化，且不改变事实和安全边界。
- 未完成来源许可审查前，系统保持本地非商业验证用途。
